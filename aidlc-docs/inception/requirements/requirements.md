## 1. 프로젝트 개요

테이블에 비치된 태블릿(브라우저)에서 고객이 직접 메뉴를 보고 주문하고, 매장 관리자는 실시간으로 주문을 모니터링·관리하는 웹 기반 테이블오더 플랫폼. 결제·배달·POS 연동 등은 범위에서 제외(`constraints.md`).

**구성 요소 4가지**
- 고객용 웹 UI (테이블 태블릿)
- 관리자용 웹 UI (매장 대시보드)
- 백엔드 API 서버
- 데이터 저장소

## 2. 확정된 기술 결정 (Technical Decisions)

| 영역 | 결정 | 비고 |
|---|---|---|
| Backend | **Python FastAPI** | REST + SSE 엔드포인트 |
| Frontend | **순수 HTML/CSS/Vanilla JS** | 빌드 과정 없음. 정적 파일로 서빙 |
| BE/FE 계약 | **API 규격을 먼저 정의**하고 BE/FE 양쪽이 준수 | 문서화된 REST/SSE 계약이 단일 진실 원천 |
| Data store | **SQLite** | 파일 기반, 재시작해도 유지 |
| 실시간 | **Server-Sent Events (SSE)** | 관리자 주문 모니터링, 2초 이내 반영 목표 |
| 관리자 인증 | **JWT 16h 세션 + bcrypt 해싱** | "로그인 시도 제한"은 MVP 범위 제외 |
| 시드 데이터 | **서버 시작 시 자동 시드** | 매장 1, 관리자 1, 카테고리/메뉴 다수, 테이블 다수 |
| Extensions | Security / Resiliency / PBT **모두 비활성** | 시간 제약, 기능 우선 방침에 따름 |

### 2.1 확정된 세부 결정 (Locked in Clarification, 2026-09-07)

| 항목 | 확정 값 |
|---|---|
| 실행/서빙 구조 | **단일 서버**: FastAPI 하나가 REST/SSE API + 정적 프론트(HTML/CSS/JS)를 함께 서빙(단일 포트, CORS 불필요) |
| 고객(테이블) 인증 | 관리자와 **동일한 JWT** 사용(테이블용 클레임: store_id, table_number, role=`table`), 브라우저 localStorage 저장, 자동 로그인 |
| 다중 매장 범위 | **단일 매장 데모 고정** (스키마에 store_id 보유, 시드 매장 1개만) |
| 고객 주문내역 UI | **단순 전체 표시**(현재 세션 주문 시간순 전체, 페이지네이션/무한스크롤 없음) |
| 주문번호 형식 | **`YYYYMMDD-HHMM-####`** (예: `20260907-1526-0001`) — 일자+시각(HHMM)+일련번호 4자리 (사용자 override) |
| 리다이렉트 대기 | 주문 성공 후 약 **5초** 뒤 메뉴 화면으로 자동 이동 |
| 대시보드 미리보기 | 테이블 카드에 **최신 주문 3개** 미리보기 |
| 신규 주문 강조 | 최근 생성 주문 색상+간단 애니메이션 강조(약 30초) |
| 메뉴 이미지 | 없거나 로드 실패 시 placeholder 이미지 |
| 과거 내역 필터 | 시작일~종료일 선택(기본 최근 표시) |
| 주문 상태 | pending(대기중) / preparing(준비중) / completed(완료) |

### 2.2 시드 데이터 (승인됨)

- **매장**: `store_id="store001"`, 매장명 "데모 식당"
- **관리자 계정**: `admin` / `admin1234` (bcrypt 해싱 저장)
- **테이블**: 6개 (`T1`~`T6`), 각 테이블 비밀번호 `0000`
- **카테고리**: 메인 / 사이드 / 음료
- **메뉴**: 카테고리별 3~4개(총 약 10개), 각 항목 가격·설명·이미지URL(placeholder) 포함

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 고객용 (Customer)

| ID | 기능 | 핵심 규칙 |
|---|---|---|
| CUST-1 | 테이블 태블릿 자동 로그인/세션 | 관리자가 1회 초기 설정(매장ID·테이블번호·테이블 비밀번호) → 이후 저장된 정보로 자동 로그인. 로그인 정보 로컬 저장 |
| CUST-2 | 메뉴 조회/탐색 | 메뉴 화면이 기본 화면. 카테고리별 분류, 메뉴명·가격·설명·이미지 표시, 카드 레이아웃, 터치 버튼 최소 44x44px |
| CUST-3 | 장바구니 관리 | 추가/삭제, 수량 증감, 총액 실시간 계산, 비우기. **클라이언트 로컬 저장**(새로고침에도 유지). 서버 전송은 주문 확정 시에만 |
| CUST-4 | 주문 생성 | 최종 확인 → 확정. 성공 시 주문번호 표시 → 장바구니 자동 비움 → 메뉴 화면으로 자동 리다이렉트. 실패 시 에러 표시 + 장바구니 유지. 주문에 매장/테이블/메뉴목록(명·수량·단가)/총액/세션ID 포함 |
| CUST-5 | 주문 내역 조회 | 주문 시간순 정렬, 주문번호·시각·메뉴·수량·금액·상태(대기중/준비중/완료). **현재 테이블 세션 주문만** 표시(이용 완료된 과거 세션 제외) |

> **주문 성공 표시 시간**: MVP 범위 문구는 "5초 표시 후 자동 리다이렉트"(4장). 본 MVP는 주문번호 표시 후 자동 리다이렉트하도록 구현하며, 표시 시간은 약 5초를 기본값으로 한다.

### 3.2 관리자용 (Admin)

| ID | 기능 | 핵심 규칙 |
|---|---|---|
| ADMIN-1 | 매장 인증 | 매장ID + 사용자명 + 비밀번호. JWT 16h 세션, 새로고침 시 유지, 16h 후 자동 로그아웃. bcrypt 해싱. 로그인한 관리자는 현재 비밀번호 확인 후 본인 비밀번호 변경 가능 |
| ADMIN-2 | 실시간 주문 모니터링 | **SSE** 실시간 갱신(2초 이내). 그리드/대시보드: 테이블별 카드(총 주문액 + 최신 주문 미리보기). 카드 클릭 시 상세. 주문 상태 변경(대기중/준비중/완료). 신규 주문 시각 강조. 테이블별 필터 |
| ADMIN-3 | 테이블 관리 | (1) 테이블 태블릿 초기 설정(번호·비밀번호, 16h 세션 생성, 자동 로그인 활성화) (2) 기존 테이블 비밀번호 재설정(재설정 후 기존 비밀번호 무효) (3) 주문 삭제(직권, 확인 팝업, 총액 재계산) (4) 세션 처리: 첫 주문 시 세션 시작 / 이용 완료 시 세션 종료 → 해당 세션 주문을 과거 이력으로 이동 + 현재 주문/총액 0 리셋 (5) 과거 주문 내역 조회(테이블별, 시간 역순, 날짜 필터) |
| ADMIN-4 | 메뉴 관리 | 카테고리별 조회, 등록(명·가격·설명·카테고리·이미지URL), 수정, 삭제, 노출 순서 조정. 필수 필드/가격 범위 검증 |

### 3.3 핵심 도메인 개념

- **테이블 세션(Table Session)**: 특정 테이블에서 첫 주문이 시작된 시점부터 "이용 완료" 처리까지의 구간. 종료 후 새 고객의 첫 주문 시 새 세션 시작.
- **주문 상태**: 대기중(pending) → 준비중(preparing) → 완료(completed).
- **과거 이력(OrderHistory)**: 세션 종료 시 현재 주문들을 세션ID로 그룹화해 이력으로 이동하고 완료 시각 기록.

## 4. 비기능 요구사항 (Non-Functional) — MVP 수준

시간 제약상 "완벽한 비기능"은 목표가 아니며, 아래는 **동작에 필요한 최소선**만 명시한다.

| 영역 | MVP 목표 |
|---|---|
| 성능/실시간 | SSE로 신규 주문 2초 이내 대시보드 반영 |
| 보안 | 관리자 비밀번호 bcrypt 해싱, JWT 16h 세션. (로그인 시도 제한·2FA·HTTPS 강제 등은 제외) |
| 데이터 지속성 | SQLite 파일로 서버 재시작 후에도 데이터 유지 |
| 사용성 | 터치 친화 UI(버튼 ≥44px), 카드형 메뉴 레이아웃 |
| 테스트 | 핵심 비즈니스 로직(세션 라이프사이클, 총액 계산, 주문 생성)에 대한 기본 단위 테스트 (전수 커버리지는 목표 아님) |
| 관측성/복원력/배포 | 로컬 실행 기준. 고가용성·모니터링·CI/CD는 범위 외 |

## 6. 대표 시나리오 (Representative Scenarios)

1. **고객 주문 흐름**: 태블릿 부팅 → 저장된 정보로 자동 로그인 → 메뉴 화면 → 카트에 담고 수량 조절 → 주문 확정 → 주문번호 표시 → 메뉴로 복귀 → "주문 내역"에서 현재 세션 주문 확인.
2. **관리자 실시간 모니터링**: 관리자 로그인 → 대시보드에 테이블별 카드 → 신규 주문이 2초 내 강조 표시 → 카드 클릭해 상세 확인 → 상태를 "준비중"→"완료"로 변경.
3. **세션 종료(이용 완료)**: 손님 퇴장 → 관리자가 해당 테이블 "이용 완료" → 확인 팝업 → 현재 주문이 과거 이력으로 이동, 테이블 총액 0 리셋 → 새 손님이 이전 내역 없이 주문 시작.
4. **직권 주문 삭제**: 관리자가 잘못된 주문 삭제 → 확인 팝업 → 삭제 후 테이블 총액 재계산.
5. **메뉴 관리**: 관리자가 신메뉴 등록(이미지 URL 포함) → 고객 메뉴 화면에 반영.

## 7. 가정 / 트레이드오프 / 리스크 (Assumptions / Tradeoffs / Risks)

**가정**
- 단일 매장 데모 규모(동시 접속 소수)를 가정. 대규모 확장성은 목표 아님.
- 고객 측 인증은 테이블 비밀번호 기반 경량 세션으로 충분(고객 개인 로그인 없음).
- 이미지는 URL 참조만 하며 업로드/최적화는 하지 않음.

**트레이드오프**
- SSE 채택(요구사항 준수) vs 폴링(더 단순): 요구사항 문구를 존중해 SSE 선택. 구현 복잡도 소폭 증가 수용.
- SQLite 채택: 셋업 속도·지속성의 균형. 동시성/확장성은 제한되나 데모 규모엔 충분.

**리스크**
- 4-5시간 제약상 UI 완성도와 엣지 케이스(동시 주문 경쟁 상태 등)는 최소화될 수 있음.
- SSE 재연결·네트워크 단절 처리는 기본 수준만 구현.

## 8. 요구사항 검증 방법 (Verification Approach)

- **기능 검증**: 6장 시나리오 1~5를 로컬 실행 환경에서 수동 워크스루로 통과.
- **자동 검증**: 세션 라이프사이클/총액 계산/주문 생성 등 핵심 로직 단위 테스트 통과(`pytest`).
- **API 계약 검증**: 사전 정의한 API 규격과 실제 BE 응답/ FE 호출이 일치.
